
## 「改为 Rust 的性能提升度」评估（2026-11-10 傍晚）

- 用户问：把本项目改成 Rust 实现能提多少性能。做法：先实测当前分解，再按瓶颈性质判语言上限，最后给杠杆重排。
- 实测（发布包 exe，1280×800，第2帧，day_night=0）：z9 57ms（面19/路19/线16/标注2，边273k/面65k/线19k）、z11 57ms（23/10/20/4，边141k/面36k/线120k）、z13 33ms（10/8/5/9）、z15 11ms、z16 7ms。分解之和与总耗时逐档吻合（z9 56≈57）⇒ 无隐藏开销，性能已完全归因。
- ★★★ **决定性证据**：`CMakeLists.txt:18` 记录「-O3 和 -march=native 都实测没有额外收益（z9 仍是 125），只留 LTO」。`-march=native` 已含自动向量化 ⇒ 瓶颈不在算术吞吐，而在内存访问 / 分支 / 每要素固定开销。Rust 走同一 LLVM 后端，**不可能突破 native SIMD 已达不到的部分** ⇒ 1:1 移植预期 0%（区间 −5%~+5%）。
- 佐证：`paint.c` 已留档「批量/向量化投影上限 6%，且唯一能拿到的 ~9ms 手段会改浮点结合顺序，整图 diff 抓到 1px」；「坐标内联进 polyrefs 只省 8ms/7%，要改落盘格式 + 重建 8 省」；AET 活动边表已把「每行扫全部边」的 25ms 消掉；pqueue D=4 是按 cache line（16B×4=64B）扫出来的。
- 现状：渲染路径**完全单线程**（`QThread` 仅用于 msleep 轮询，无 OpenMP/无 intrinsics）；28 处 cache line/L2/L3 优化注释 ⇒ 数据结构已按缓存设计。
- 真正的杠杆（与语言无关）：①多线程分带渲染，面/路/线共 54ms/57ms 可并行，8 核理论 6×、实际受标注串行+带宽限制 3-4×；②LOD 档位，`AREA_DOT_PX` 2→3 实测省 15%（项目已有旋钮，属画质取舍）。
- 结论口径：纯换语言 0%；Rust+并行+LOD 的 3.5-4.5× **全部来自并行与 LOD，0% 来自语言**。31,075 行 C/H + 逐字节等价门禁（87 regress / 121 ui-test / 出图 cmp）⇒ 全量重写估 6-10 人月且极可能拿不到速度。
- 建议：先做 C 多线程分带验证上限（1-2 周），Rust 只用于新增模块或 tools/；若要证伪本结论，取 `fill_polygon`+`raster_hspan` 约 300 行 1:1 翻 Rust 对拍 BMP，1-2 天即可出数。

## 分带并行渲染落地（2026-11-10 晚，commit d8ed879）

- 用户拍板「直接开始分带并行的方案」。新增 `src/render/band.{c,h}`：切带 + 阻塞式线程池（spawn detached + mutex/cond 计数，spawn 失败主线程补跑并扣账）。`SKEDADDLE_BANDS`：0=串行基线 / N=强制 / 缺省=核数≤8；`sk_cpu_cores()` 进 plat.{c,h}。
- 三阶段（面/线/路）各建 Ctx 快照 + `*_emit` 单要素函数，串行与并行共用同一份代码；要素按带分桶，每条相交带各画一次（clip 过滤），审计计数只归主带=首条相交带。
- 实测（发布包 exe，1280×800 北京中心，4 轮取最小，面/路/线 ms）：z9 20/18/19→10/13/10、z11 26/10/24→9/5/18、z13 15/9/5→6/6/4、z15 4/2/3→2/1/3。阶段和 z9 57→33ms（~1.7×）、z11 60→32（1.9×）、z13 29→16（1.8×）。
- ★ 验收：z9/z11/z13/z15/z16 出图与串行逐字节一致（cmp）；带数 2/3/4/5/7/8/16 全一致；门禁 check_layers PASS；Windows regress 64/24（FAIL 全是多省/rev.bin/lm.bin 环境缺失；area_lod 期望 117212 是 8 省口径）；ui-test 0 FAIL 退出码 0。HEAD 对照：串行出图与改动前逐字节一致、areas_drawn 同为 65132（6 面差异是更早提交的，非本次）。

### ★★★ 分带并行的四个像素级陷阱（都实测踩过，别再犯）
1. **跨带线段不能从裁剪端点重跑 Bresenham**：`raster_clip_line` 会重建端点，重跑漂 1px（~34% 跨界段）。修法=对**画布**矩形裁剪（端点与串行逐字节相同），再逐像素按带过滤 ⇒ `raster_line_checked`；前提是所有写原语尊重 `Raster.clip`（serial 时 clip=全画布，行为不变）。
2. **路分桶余量 ≠ 视口 margin**：带归属只需 ±3 行（width5 描边 y±2 + 量化 1）。把 margin 64 搬进来 ⇒ 带（100 行）两两重叠 134 行，z9 平均每边被 2.3 带重画（63.8 万 push/27.4 万边），**路 19ms 反而变 23ms**。
3. **road_emit 带早退判据必须比分桶范围宽 4 行**：判据相等时，边界行上的边"分进来了又立刻退掉"，既不画也不计数（z13 少 25 条、z15 差 21 像素；z9 计数差 1094）。clip 兜底，判据只是提速。
4. **路名锚点不能"落在本带才收"**：串行无条件收（from 端点在画布内、中点在画布外的长边也收，labels.c 自己裁）。按带收 ⇒ 收集集合不同 ⇒ 避让结果变（z15 底缘 651 像素 = 多/少一个路名标签及其白描边）。修法=锚点钳到端带（tgt=clamp((ay-cy0)*nb/cyh)），每边恰收一次，按 seq 归并还原串行序。

### ★ 离屏出图必须从仓库根目录跑（本次最大的假象）
- POI 图标与地名数据按 **cwd 相对路径**找：从 `dist/skedaddle-release/` 里跑 `--shot-offscreen` ⇒ `place_labels=0`、`poi_icons=0`，整图差 4.2%（白字全没）。b0/b8 两侧一致时 cmp 结论不受影响，但与历史基线/HEAD 对拍会假 DIFF——排查"文字消失"先看 cwd 与 `place_labels` 计数。
- Windows 跑 regress 需运行时 PATH：`export PATH="/e/skedaddle/dist/skedaddle-release:/d/msys64/ucrt64/bin:$PATH"`（Qt6 DLL + libprotobuf-c）。编译期 PATH 仍绝不能放 Qt bin。
- regress 跑完会写 view_* 进真实 settings.ini ⇒ 跑前备份、跑完恢复（本次已恢复）。

## 标注阶段并行 + LOD 档位（2026-11-10 晚，commit ff5dfae + b5fc793）

### 标注阶段并行（决策串行 + 命令列表 + 分带绘制）
- 结构：网格避让是先到先得的链式决策 ⇒ 决策必须串行；绘制（白描边 = 同文字 8 邻域画 10 遍）压成 LabelCmd（type/x/y/text/font/颜色/行包围盒），flush 时 band_run 分带执行。每条命令交给**所有**与其行包围盒相交的带（clip 过滤），带内按命令序 ⇒ 每像素写入序与串行相同 ⇒ 逐字节一致。
- ★★★ **font_draw 的 y 是基线**，字形向上伸约 ascent；且 hhea ascent 不是 CJK 字形的可信上界（28px 大字实测顶伸基线上方 22 行，metrics 只给 12）⇒ 新增 `font_vbox()` = max(metrics_ascent, 0.9×ptsize)+1。估小了就是"每条带边界上方缺字"（z11 门头沟区 100 像素、z15 每边界上方 6 行 1914 像素）。POI 标记的行包围盒要按 R+1≤13 给。
- ★★★ **字形缓存是懒插入共享哈希，8 线程 glyph_get 会把互斥锁打成热点：标注 21ms→129ms（比串行慢 6 倍）**。修法 = flush 前主线程串行 `font_warm_text` 预热本帧全部文本（稳态=每码点一次哈希），worker 走 `font_draw_a_pre`（glyph_find 无锁只读）。**串行路径同样预热**——单带也走 glyph_find，不预热首帧缺字。这个全局锁保留着：只防非预热路径的竞态。
- 实测：标注 z13 12→6ms、z15 11→5ms（2×，b4 略优于 b8）；z9~z16 与改动前逐字节一致。
- ★★★ **本机最大的坑（再犯一次）**：cc_retry/build_launcher 包装器会吞真实编译错误（stderr 空 + ninja FAILED）⇒ `cmake --build` 报成功、跑的是旧 exe，连续两轮"验证通过"全是旧二进制。判据：看见 `FAILED: ... cc.exe` 就**绕过包装器直接 `cc -fsyntax-only` 看真 stderr**（这次是 `big` 未声明：vbox 调用插在 `Font *big = ...` 声明之前）。修完先 syntax-only 再 build。

### LOD 档位（AREA_DOT_PX → 设置项 lod_area）
- paint.c 运行时档 `g_area_dot_px`（钳 2~12）+ `paint_set_area_dot_px()`；缺省 = 编译期 4，不写键出图逐字节不变。
- settings.c「小面简化」ST_INT 4/2~12；★ settings 在分层 DAG 里位于 render **下游**，不能 include paint.h 拿缺省常量（check_layers 拦）⇒ 字面值 4 + 注释锚点，改默认值两处一起改。
- window.c 三处接线（app_init / app_apply_settings / app_persist_settings）与 max_class 同构。
- 实测：areas_dotted 随档位单调（z9 55414@3 < 59793@4 < 64468@12），面阶段 z9 10→7ms、z13 6→4ms；lod_area=99 钳到 12。
- 注意：离屏通道不调 app_persist_settings（不回写 ini），持久化接线与 max_class 同构、未真机验证回写。

## 外部 POI 支持（2026-11-10 晚，commit a11ff6d）

- 设置项 `poi_source`（ST_INT 枚举 0=地图自带/1=外部文件），面板「POI 来源」。**只接管设施 POI（kind 11）一层**，行政地名（kind 1~10）永远来自 places_auto.db。外部文件 `products/poi_ext.csv`（SKEDADDLE_POI_EXT 可覆盖），格式 `名称,纬度,经度[,权重]`，kind 恒 11，权重缺省 50（量纲=places_build：车站60/医院50）。init 时整表载入内存，不热重载；地名库打不开也能纯外部跑。
- 合并语义：poi_source=1 时 SQL 层排除内置 kind 11（?7 = show_poi && source==0），视口内条目并入后按 weight 降序合并 Top-N（两层共享名额；并列时 SQL 序在前=行政地名优先）。show_poi=0 / zoom<13 时不并入（与内置口径一致）。切换来源即失效 LabelCache（cached_poi_source 进缓存判据）。
- ★★★ **避让按列表序先到先得 ⇒ 合并后必须重排序，不能只在超 Top-N 时排**：外部条目不排就永远最后入场，w=500 的中心点也会被先到的村名抢格挤掉（实测 poi_icons 少 1 且无异常）。顺带修掉残留越界循环（qsort 后旧代码还按 limit 读只有 n_items 项的序号数组 ⇒ 段错误；这正是"cmake 报成功但旧 exe 在跑"之外的另一类坑：**补丁替换块时旧语句残留**，-fsyntax-only 查不出来，靠 rc=139 + 二分带数/串行才定位）。
- 实测：poi_source=0（含不写键）出图与基线逐字节一致；=1 时内置 74 个设施 POI 让位、外部 3 点上图（目检）；z12 两来源逐字节一致。门禁：check_layers 0 违规、ui-test 0、regress 64/24 同基线。搜索不含外部 POI（bigram 只建库时生成）——要可搜走 places_build --extra 路线（未做）。
